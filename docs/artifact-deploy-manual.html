Manual de Despliegue

Cómo levantar, desplegar y mantener Monix en producción, de punta a punta. Pensado para cualquiera del equipo — o el profesor — que necesite entender el circuito sin reconstruir el contexto desde cero.

Monix es 100% web: un mismo build se despliega una sola vez y se instala como PWA en desktop, iOS y Android. No hay build nativo ni distribución por APK. La versión con todo el detalle vive en docs/manual-despliegue.md del repo.

1 Arquitectura

flowchart LR
  U["Usuario · desktop / iOS / Android"] -->|HTTPS, instala la PWA| V["Vercel · estático + PWA"]
  V -->|REST / Realtime| S[("Supabase · Postgres + Auth + RLS")]
  V -->|invoke| EF["Edge Functions · Deno"]
  V -->|proxy /bc-api| BC["Banco Central · API de la cátedra"]

Un solo frontend sirve a los tres sistemas operativos. El Banco Central es la API externa compartida por la cátedra — nunca se llama directo desde el navegador, siempre vía el proxy /bc-api.

PiezaQué esDónde vive
FrontendReact + TypeScript + Vite, PWA con Workboxsrc/
HostingVercel, deploy automático al pushear a mainproyecto Vercel ↔ GitHub
BackendSupabase: Postgres + RLS, Auth, Realtime, Edge Functionssrc/lib/supabaseClient.ts
API externaBanco Central de la cátedra (interbancario simulado)centralbank.brocoly.cc vía /bc-api
ⓘ
Un solo entorno: no hay staging, main es producción. Para algo riesgoso (una migración destructiva) conviene crear una rama de base de datos temporal en Supabase antes de tocar la real.

2 Puesta en marcha en local

terminal
git clone https://github.com/Maxi12141/HomebankingMonix.git
cd HomebankingMonix
npm install
cp .env.example .env.local   ## completar con los valores reales, ver §3
npm run dev                  ## http://localhost:5173
ComandoPara qué
npm run devServidor de desarrollo con hot reload
npm run buildtsc && vite build — build de producción en dist/
npm run previewSirve el build real localmente antes de pushear

No hay suite de tests automatizada ni CI (no existe .github/workflows). La única red de seguridad antes de un deploy es que tsc falle si hay un error de tipos, y el checklist de §9 — por eso ese checklist importa tanto.

4 Frontend en Vercel

flowchart LR
  A["git push a main"] --> B["Vercel: npm run build"]
  B --> C{"¿tsc ok?"}
  C -->|no| X["Deploy rechazado"]
  C -->|sí| D["vite build → dist/"]
  D --> E["Producción"]
  E -.rollback.-> F["Promote a un deploy anterior"]

npm run build corre tsc && vite build — un error de tipos frena el deploy a propósito, antes de que suba nada roto.

Lo que vercel.json hace y no es opcional

  • Reescribe /bc-api/:path* → centralbank.brocoly.cc/api/:path*. Sin esto el Banco Central no responde en producción aunque funcione en local.
  • Fuerza Cache-Control: no-cache en index.html — si no, el service worker deja a la gente pegada en una versión vieja indefinidamente.
  • Permissions-Policy habilitando cámara/micrófono/NFC/WebAuthn — sin esto el navegador bloquea esos permisos aunque el usuario los acepte.

Rollback

Vercel → Deployments → elegir uno anterior bueno → "Promote to Production". Inmediato, no requiere tocar git (igual conviene revertir el commit para que main no mienta).

5 Backend en Supabase

Migraciones

Archivos sueltos en supabase/*.sql, se aplican a mano (SQL Editor de Supabase Studio, o MCP apply_migration). Orden: policies.sql primero (RLS), transferencia_atomica.sql al final.

Edge Functions

terminal
npx supabase functions deploy firmar-qr --project-ref <ref>

Supabase no agrega CORS solo: toda función nueva necesita manejar OPTIONS y devolver Access-Control-Allow-Origin a mano. Secrets en Dashboard → Edge Functions → Secrets.

Auth — en un proyecto Supabase nuevo

  • "Confirm email" debe estar desactivado (Authentication → Settings): el registro llama a signUp() esperando que el usuario quede logueado al toque. Con la confirmación activa, queda sin sesión y el alta se ve "rota".
  • Redirect URLs: agregar <url-de-producción>/restablecer-contrasena (y el de localhost:5173) en Authentication → URL Configuration, o el link de "olvidé mi contraseña" se rechaza.
  • La plantilla de mail con la identidad de Monix vive en docs/email-recuperar-contrasena.html — pegarla en Authentication → Email Templates → Reset Password.

6 PWA — instalación en desktop, iOS y Android

  • Manifest e iconos generados por vite-plugin-pwa, assets en public/.
  • Registro manual en main.tsx (no automático) para controlar el aviso de actualización con toast propio (registrarPwa.tsx).
  • El botón "Instalar" (usePwaInstall.ts + pwaInstallPrompt.ts) depende de que el navegador dispare beforeinstallprompt — requiere HTTPS real y que el manifest + service worker pasen los criterios de instalabilidad de Chrome.
  • Verificar instalabilidad: DevTools → Application → Manifest / Service Workers, o Lighthouse → PWA.

Compatibilidad real del botón "Instalar"

NavegadorComportamiento
Chrome / Edge (Android y desktop)Dispara beforeinstallprompt, instalación con un tap
Safari (iOS y macOS)Nunca dispara el evento — paso manual (Compartir → Agregar a Inicio)
Firefox (cualquier plataforma)No soporta el evento — el botón cae a "no disponible"

7 Seguridad — qué no romper

  • RLS siempre activo en toda tabla nueva. Una tabla sin política es una tabla que cualquier usuario autenticado puede leer/escribir entera.
  • service_role nunca va al frontend. Sólo anon (protegida por RLS) sale en VITE_SUPABASE_ANON_KEY. Si hace falta saltar RLS a propósito, sólo dentro de una Edge Function.
  • Permissions-Policy en vercel.json es lo que permite pedir cámara/NFC/WebAuthn — no sacarla al tocar ese archivo.
  • Rate limiting es sólo del lado del cliente (backoff progresivo en LoginPage.tsx) — no hay límite real del lado del servidor. Limitación conocida, no un bug a arreglar.
  • Nunca commitear .env.local ni ninguna clave — si igual pasa, rotarla, no alcanza con borrar el commit.

8 Monitoreo y logs

No hay error tracking integrado (Sentry o similar) — el diagnóstico en producción es manual:

Qué pasóDónde mirar
El build falló en VercelVercel → Deployments → el deploy en rojo → Build Logs
Algo falla ya desplegado (runtime)Consola del navegador — es una SPA estática, sin logs de servidor propios
Una Edge Function fallaSupabase Dashboard → Edge Functions → Logs
Dudas sobre RLS/datosSupabase Dashboard → Table/SQL Editor
